# Протокол v2

Протокол между клиентом и сервером задаёт крейт `cypher-wire`. Сервер понимает только эти сообщения; всё, что связано с перепиской, лежит внутри непрозрачных полей `body`, и их разбирает только клиент (`cypher-core`). Константы и лимиты ниже взяты из кода — при расхождении прав код.

## Транспорт

| Канал | Кто пользуется | Кадрирование |
|---|---|---|
| TLS, порт 9100 (gateway) и 9300 (relay) | нативные клиенты | `[u32 BE длина][кадр]`, кадр ≤ 1 МиБ |
| WebSocket `/ws` (gateway) и `/relay` (relay) за TLS-прокси | браузер | одно бинарное WS-сообщение — один кадр |

## Кадр

```text
[kind u8][req_id u32 LE][поля...]
```

- **Кодировка.** Целые числа — little-endian, байтовые строки — с префиксом длины `u32`.
- **`req_id`.** Выбирает клиент; ответ сервера несёт тот же `req_id`. Сообщения, которые сервер шлёт сам (`Recv`, `Superseded`), идут с `req_id = 0`.
- **Разбор.** Неизвестный `kind`, лишние байты в конце и превышение лимитов — ошибка разбора. На всё это есть fuzz-цели.

## Вход в сессию (gateway)

```text
клиент                                  gateway
Hello {version = 2, peer}      ──►
                               ◄──      Challenge {nonce[32]}
Auth {Ed25519(nonce)}          ──►      подпись по "cypher-session-auth-v2" ‖ nonce
                               ◄──      Ready
```

- **`PeerId`** — открытый ключ Ed25519, то есть владение ключом и есть аутентификация. Другая версия протокола отклоняется.
- **Тайм-ауты.** На аутентификацию — 10 с. Соединение без трафика закрывается через 60 с; клиент держит его сообщениями `Ping`/`Pong`.
- **Одна сессия на личность.** Новый вход с той же личностью вытесняет старый: старая сессия получает `Superseded` — на этом узле или на другом через NATS.

## Сообщения

### Пересылка (gateway)

| Kind | Сообщение | Поля |
|---|---|---|
| `0x10` | `Send` (клиент) | `to[32]`, `want_ack u8`, `body` до конца кадра |
| `0x11` | `Recv` (сервер) | `from[32]`, `body`; `from` ставит gateway из сессии — подделать отправителя нельзя |
| `0x12` | `SendAck` (сервер) | `status`: 0 доставлено, 1 получатель офлайн, 2 перегружен |

Если получатель подключён к другому узлу, gateway передаёт кадр через NATS-субъект `peer.<id>` и ждёт ответа до 3 с. Лимиты на соединение: 2000 кадров/с и 64 МиБ/с; сверх лимита кадры отбрасываются. Очередь на отправку клиенту — 8 МиБ; если она переполнена, отправитель получает `Busy`.

### Ключи и ссылки (signaling через gateway)

| Kind | Запрос → ответ | Смысл |
|---|---|---|
| `0x20` → `0x23` | `PublishKeys{base[164], opks[], replace}` → `KeysAck{opks_left}` | Публикация prekey-бандла: личность, X25519-ключ, подписанный prekey, подпись; до 200 одноразовых ключей за раз. Чужой бандл отклоняется. |
| `0x21` → `0x22` | `FetchKeys{peer}` → `Keys{base, opk?}` | Бандл собеседника и один одноразовый ключ; ключ выдаётся один раз. |
| `0x30` → `0x32` | `CreateLink` → `LinkCreated{link}` | Ссылка-приглашение, живёт 24 ч. |
| `0x31` → `0x33` | `ResolveLink{link}` → `LinkResolved{peer}` | Кому принадлежит ссылка. |
| `0x50` → `0x51` | `Bootstrap` → `BootstrapInfo{relay_addr, onion_key, capabilities}` | Где relay и чем запечатывать onion-запросы. |

Gateway передаёт запрос в NATS `sig.req` с заголовком `cy-peer` — это аутентифицированная личность. Эти запросы требуют личности; анонимно их задать нельзя (ответ `Unauthorized`).

### Inbox — офлайн-доставка

| Kind | Запрос → ответ | Смысл |
|---|---|---|
| `0x40` → `0x44` | `InboxPut{inbox[32], item}` → `Done` | Положить запечатанный элемент (≤ 72 КиБ) в чужой inbox. |
| `0x41` → `0x43` | `InboxFetch{secret[32]}` → `InboxBatch{claim[16], items[]}` | Захватить до 64 элементов (≤ 768 КиБ) на 120 с. |
| `0x42` → `0x44` | `InboxAck{secret, claim}` → `Done` | Удалить захваченное. Без подтверждения элементы вернутся в inbox. |

- **Адрес inbox** — `SHA-256("cypher/v2/inbox" ‖ secret)`. Владелец сообщает адрес собеседникам внутри зашифрованного конверта `Hello`. Писать может любой, кто знает адрес; читать и удалять — только тот, кто знает `secret`.
- **Лимиты хранения:** элементы живут 14 дней, в одном inbox — не больше 1000.
- **Как ходят запросы.** Все три запроса к inbox клиент отправляет через relay, то есть анонимно. Прямо через gateway они идут, только если анонимный режим выключен, а relay недоступен.

### Прочее

| Kind | Сообщение |
|---|---|
| `0x05` / `0x06` | `Ping` / `Pong` |
| `0x07` | `Superseded` — та же личность вошла в другом месте |
| `0x7F` | `Error{code}`: 1 NotFound, 2 BadRequest, 3 RateLimited, 4 Unauthorized, 5 TooLarge, 6 Unavailable, 7 Internal |

## Onion-канал (relay)

Кадр клиента к relay выглядит так: `[corr u64][запечатанный запрос]`. Ответ приходит с тем же `corr`, поэтому запросы можно отправлять конвейером — до 8 одновременно на соединение.

1. Клиент берёт кадр inbox-запроса, добавляет метку времени и свежий ключ для ответа. Всё это он запечатывает на onion-ключ signaling (X25519, из `Bootstrap`) и дополняет до фиксированного размера: 1, 4, 16 или 96 КиБ.
2. Relay публикует запрос в NATS `sig.onion`, без личности и без адреса клиента.
3. Signaling открывает запрос и отбрасывает его, если метка времени расходится с его часами больше чем на 120 с — это защита от повтора. Затем выполняет запрос и шифрует ответ ключом ответа, дополняя до того же набора размеров.
4. Relay возвращает ответ клиенту. Прочитать или подделать запрос и ответ он не может.

Лимиты relay: запрос ≤ 128 КиБ, 20 кадров/с и 1 МиБ/с на соединение, простой — 5 мин. Десктоп в анонимном режиме подключается к relay через Tor (arti, по желанию с мостами); подробнее — в [threat-model.md](threat-model.md).

## End-to-end уровень (внутри `body`)

Формат `body` задаёт `cypher-core/src/relay.rs`; сервер его не разбирает.

| Тег | Что | Содержимое |
|---|---|---|
| 0 | сообщение | заголовок X3DH (только в первом сообщении), заголовок ratchet, шифртекст конверта |
| 1 | чанк файла | `file_id[16]`, `index u32`, шифртекст чанка |
| 2 | подтверждение чанков | `file_id`, `next`, `sack u64` (битовая маска после `next`), тег аутентичности |

- **Сессия.** X3DH (схема Signal): инициатор — тот, кто перешёл по ссылке. Заголовок инициализации подписан его Ed25519-ключом, что связывает X25519-ключ с `PeerId`. Дальше — Double Ratchet.
- **Конверт** (`envelope.rs`, postcard) — одно из:
  - `Hello{inbox}`;
  - `Text{text ≤ 16 КиБ, reply_to}`;
  - `File{описание, вид}` — обычный файл, голосовое с волной или кружочек с постером ≤ 16 КиБ;
  - `FileCtl` — `Accept` с битовой картой уже полученных чанков или `Cancel`;
  - `Receipt` — доставлено/прочитано, до 512 id.

  Перед шифрованием конверт дополняется, чтобы скрыть точную длину: до степени двойки от 256 байт до 64 КиБ, дальше — до кратного 64 КиБ.
- **Файлы.** До 64 ГиБ. Чанки по 256 КиБ, медиа — по 64 КиБ; у каждого файла свой ключ AES-256-GCM внутри описания. Подтверждения чанков аутентифицированы ключом файла, поэтому сервер не может подделать прогресс. Файл до 32 КиБ едет прямо в конверте.
- **Офлайн-элемент inbox** запечатан sealed sender'ом: ECIES на X25519-ключ получателя плюс AES-256-GCM. Внутри — `PeerId` отправителя и `body` сообщения. Сервер хранения не видит ни отправителя, ни содержимого.
- **Prekeys.** Клиент держит в запасе 100 одноразовых ключей и доливает их, когда на сервере остаётся меньше 20. Подписанный prekey сменяется раз в неделю. Бандл живёт на сервере 30 дней.
