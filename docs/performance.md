# Производительность «Шифра»: замеры, профили, цели

Числа ниже получены на коде ветки `dev` после фазы F2 и воспроизводятся командами из последнего раздела. Каждое значение сверено как минимум двумя независимыми инструментами. Если числа меняются, этот документ обновляется в том же коммите.

## Стенд
- AMD Ryzen 9 9900X (12 ядер / 24 потока), 32 ГБ.
- Нагрузка — Linux в Docker Desktop (WSL2, 24 vCPU, 16 ГБ).
- Сервисы собраны профилем release: `lto = "fat"`, `codegen-units = 1`, `panic = "abort"`. Для perf — профиль `profiling`: тот же код плюс символы и frame pointers.
- Генераторы нагрузки работают на той же машине, что и сервисы. Их собственная работа входит в задержки. Для k6 это заметно: при 2000 парах он занимает 4.4 ядра против 1.3 у всего стенда.

## Найдено и исправлено
1. **tungstenite обнулял 128 КиБ перед каждым чтением из сокета.**
   - Найдено через perf: 10% CPU gateway в `memset`.
   - `FrameCodec::read_in` расширяет буфер до `read_buffer_size` нулями, и эта память становилась резидентной у каждого WebSocket-соединения.
   - Исправление: `read_buffer_size` 8 КиБ (`crates/cypher-transport/src/ws.rs`).
2. **Общий токен остановки.**
   - Каждая задача соединения опрашивала один `CancellationToken`, и все воркеры сериализовались на мьютексе его списка ожидающих.
   - Исправление: у каждого соединения свой дочерний токен.
3. **Новый таймер простоя на каждый кадр.**
   - Вставка в колесо таймеров tokio и удаление из него на горячем пути (`TimerEntry::reset` в профиле).
   - Исправление: у сессии gateway и соединения relay один таймер; он перевзводится, только когда срабатывает.

   **Итог трёх правок** на одной нагрузке (1500 пар, 854 тыс. сообщений):
   - CPU gateway на сообщение: 56 → 42 мкс на узле отправителя, 51 → 33 мкс на узле получателя;
   - RSS после прогона: 152 → 62 МБ;
   - подтверждение p99: 5 → 4 мс;
   - WebSocket-соединение стоит ≈24 КБ, столько же, сколько TLS-соединение (раньше ≈100 КБ).
4. **Caddy отдавал хэшированные `/assets/*` с `Cache-Control: no-cache`.**
   - Найдено через wrk и `curl -I`. Одноимённые директивы сортируются по специфичности матчера, и общий `header` без матчера перетирал правило для ассетов.
   - Исправление: два взаимоисключающих матчера.
5. **Сжатие на каждый запрос.**
   - Сборка PWA теперь кладёт рядом с файлами `.br`, `.zst` и `.gz` на максимальных уровнях (`apps/pwa/scripts/precompress.mjs`), Caddy отдаёт их через `precompressed`.
   - wasm: 823 КБ → 257 КБ (сжатие на лету давало 335 КБ).
   - JS-бандл: 7 тыс. → 36 тыс. запросов/с, p99 31 → 10 мс.
6. **Фича `console` роняла сборки с `--all-features`.** `console-subscriber` паникует без `--cfg tokio_unstable`. Теперь слой подключается только с этим флагом.
7. **`cargo bench --benches` падал на флагах criterion.** В цели попадал libtest-бенчмарк библиотеки. В бенчмарк-крейтах стоит `[lib] bench = false`.

## Проверено, замечаний нет
- **Утечки задач.** `tokio_alive_tasks` возвращается к исходному значению после каждого прогона: TLS, WebSocket, смена подключений. CI проверяет это автоматически (`--assert-tasks-return`).
- **Эндпоинт метрик.** 8.7 тыс. скрейпов в секунду — в 130 тыс. раз чаще Prometheus — не изменили пропускную способность и p99 доставки. В проде эндпоинт слушает только `127.0.0.1`.
- **tokio-console.** Ни одного `lost-waker`, `self-wakes` или `never-yielded`. `large-future` — это ожидание межузлового подтверждения (1.4 КБ, живёт миллисекунды) и задача соединения (2.2 КБ).
- **FFI под memcheck:** тесты `cypher-media` с libopus и `cypher-client` с SQLite — 0 ошибок, 0 утечек.

## Известные ограничения и возможности
- **Аллокации при межузловой пересылке с подтверждением.** 1.8 КБ на кадр, почти всё — задача ожидания ответа NATS. Это около 5% CPU на malloc/free. Уйти от этого может общий reply-субъект на gateway с таблицей корреляции вместо inbox на запрос. Это смена дизайна, делать её стоит при реальной нужде.
- **AES-GCM из RustCrypto.** ≈1 ГБ/с, 8.2 инструкции на байт; GHASH на `PCLMULQDQ` без агрегированной редукции. AEAD из ring дал бы примерно ×4, но это уже больше пропускной способности сети.
- **Опрос токенов отмены.** Около 2% CPU. Чтобы убрать его полностью, нужен один `select` на соединение, то есть смена трейта `Handler`.
- **Точность k6.** Задержки в k6 меряются настенными часами с точностью до 1 мс, поэтому субмиллисекундные значения точнее у `tools/load-test`.

| Пар | Ошибки, Offline, Busy | Подтверждение p50 / p99 | Доставка p50 / p99 | Сообщений/с | Память на соединение |

**Статика PWA** (wrk, 100 соединений, файлы внутри контейнера Caddy):

| Цель | Запросов/с | p50 / p99 |
|---|---|---|

## Память на соединение
Состав после всех правок, по heaptrack, massif, tokio-console и RSS:
- rustls — ≈4 КБ;
- буферы соединения — 2×2 КиБ (TLS) или 8 КиБ буфер чтения (WebSocket);
- одна подписка NATS — 6.4 КБ;
- задача соединения — 2.2 КБ;
- исходящая очередь и прочее.

Итог — 17 КБ кучи, 18–24 КБ RSS.

**История:**
- фаза F: 38.3 → 24.5 КБ (TLS) за счёт одной подписки NATS вместо двух и буферов `Framed` по 2 КиБ;
- фаза F2: WebSocket-соединения ≈100 → ≈24 КБ за счёт буфера tungstenite.

Рост RSS между повторными прогонами — это удержание памяти аренами glibc, а не утечка: с `MALLOC_ARENA_MAX=2` рост затухает. Замена аллокатора на mimalloc проверена и отклонена: у него выше пиковый расход.

**Ёмкость одного узла gateway:**
- 10 тыс. клиентов ≈ 250 МБ;
- 100 тыс. ≈ 2.5 ГБ плюс удержание после пиков.

Порог в CI — **≤ 40 КБ на соединение**.

## Как воспроизвести
```sh
just bench                         # criterion; just bench -- ratchet — выборочно
just load 2000 30                  # нативный TLS против локального gateway
just load-ws 500 60s               # k6 по WebSocket (нужен k6)
just console gateway               # сервис с tokio-console, затем `tokio-console`
scripts/flamegraph.sh build        # профиль profiling с frame pointers
just flamegraph gateway 30         # SVG в target/flamegraphs/ (Linux, perf, inferno)
```

**wrk против статики PWA:**
```sh
docker compose up -d pwa
wrk -t4 -c100 -d20s --latency -H 'Accept-Encoding: br' http://127.0.0.1:8080/
```

**Особенности Docker Desktop (WSL2):**
- perf работает только в `--privileged` контейнере с `-e cpu-clock`;
- `process_*`-метрики есть только на Linux;
- для k6 используйте несколько пар на VU (`PAIRS_PER_VU`): каждый VU — отдельный JS-рантайм, и тысячи VU исчерпывают память VM.

**Ручная процедура на 100 тыс. соединений** (отдельная Linux-машина):
1. Поднять лимиты:
   - `ulimit -n 1048576`;
   - `sysctl -w net.ipv4.ip_local_port_range="1024 65535"`;
   - `sysctl -w net.core.somaxconn=65535`.
2. Добавить loopback-алиасы `127.0.0.2…127.0.0.5`.
3. Запустить `load-test --src-ips 127.0.0.2,127.0.0.3,127.0.0.4,127.0.0.5 --connections 100000 --ramp 120 --metrics-addr … --assert-tasks-return 5`.
4. Записать результаты сюда.
