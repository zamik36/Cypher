# Roadmap — Шифр (Cypher)

> Обновлено: 6 октября 2026. Откуда взялись задачи — в [assessment.md](assessment.md), что уже сделано — в [report-2026-09.md](report-2026-09.md).

## Где мы сейчас

Ядро, криптография, протокол и сервисы готовы и проверены: этапы 0–6 и доводка A–H. Этап 1 закрыт 4 октября 2026 (итоги — в [assessment.md](assessment.md#этап-1-закрыт)). Этап 2 выполнен в коде; осталось то, что требует ваших аккаунтов и ключей (ниже). Этап 3 — в работе: новый интерфейс, файлы в чате, имена контактов и сканер QR готовы.

**Порядок дальше:** закрыть этап 3 (A1–A6 ниже) → запуск (VPS, подписанные сборки, магазины — этап 2.4/2.10) → push-уведомления (4.2) → скрытие метаданных, группы, несколько устройств. Платформы: Android, Windows, PWA; macOS и iOS — позже.

| Этап | Цель | Итог |
|---|---|---|
| 1 | Безопасность и целостность данных | Нет известных способов сломать сессию, засорить сервер или потерять данные при обновлении |
| 2 | Эксплуатация и выпуск | Предсказуемый деплой с откатом, подписанные и самообновляемые клиенты, алерты |
| 3 | Продукт: базовый уровень мессенджера | Пользователю хватает возможностей и понятны состояния |
| 4 | Версия 1.0 | Несколько устройств, push-уведомления, скрытие метаданных |

Размер: **S** — до пары дней, **M** — около недели, **L** — 2–3 недели, **XL** — больше месяца.

## Этап 1. Безопасность и целостность данных — выполнен

| # | Задача | Размер | Готово, когда |
|---|---|---|---|
| 1.1 | **Сверка ключа при знакомстве.** В ссылке и QR — отпечаток ключа хозяина; клиент сверяет его с ключом от сервера и отказывает при расхождении. Экран кодов безопасности для уже знакомых. | M | Подмена ключа сервером при знакомстве обнаруживается тестом стека. |
| 1.2 | **Версии хранимых данных.** Тег версии в записях ядра; миграции; SQLite `user_version`; версия схемы IndexedDB. Нечитаемая запись помещается в карантин и не обрывает запуск. | M | Тест: база предыдущей версии открывается новой сборкой. |
| 1.3 | **Квоты inbox и памяти Redis.** Лимит байтов и элементов на inbox без продления TTL при записи; `maxmemory` с политикой; `TooLarge` — отдельный исход у клиента. | M | Нагрузочный тест засорения inbox не выводит Redis за лимит. |
| 1.4 | **Prekeys.** Обрезка списка одноразовых ключей; rate limit `FetchKeys` на того, кто спрашивает, и на цель; ротация не выталкивает выданные ключи, пока есть невыданные. | S | Тесты signaling и ядра на «выпивание» и ротацию. |
| 1.5 | **Лимиты по IP и по личности.** Реальный адрес клиента от Caddy (заголовок или PROXY protocol); лимиты соединений и запросов по IP в gateway и relay; лимит межузловых задач; раздельные семафоры для onion и аутентифицированных запросов в signaling; лимит `CreateLink`. | M | Тесты отказа для каждого лимита; нагрузка в CI зелёная. |
| 1.6 | **Перечитывание TLS-сертификатов** gateway и relay без рестарта. | S | Тест: замена файлов сертификата подхватывается. |
| 1.7 | **ACL NATS.** Отдельный префикс inbox у каждого пользователя (`_INBOX_gw.>`, `_INBOX_relay.>`), ответы через `allow_responses`. | S | Relay не может подписаться на ответы gateway — проверка на живом NATS. |
| 1.8 | **Квитанции о прочтении.** Только для сообщений, реально показанных в активном окне; локальный статус «прочитано»; без повторной отправки. | S | Тест стора и Playwright: квитанция уходит один раз. |
| 1.9 | **Переподключение.** Backoff с jitter; повторы отправки с экспонентой и пределом; ответ сервера о несовместимой версии → в UI «нужно обновление». | S | Тесты ядра и драйвера. |
| 1.10 | **Мелкая гигиена.** `verify_strict` для Ed25519; пределы параметров Argon2 при импорте; проверка содержимого файла при возобновлении передачи. | S | Модульные тесты. |

Сделано: деплой по sha с откатом и защищённым триггером (2.1), `/ready` и healthcheck'и (2.2), образы на каждом PR и `:latest` только после полного CI (2.3), единая версия, CHANGELOG, SBOM, provenance и подпись образов (2.5), алерты, дашборды, экспортёры, retention и ротация логов (2.6), изоляция контейнеров (2.7), бэкапы с проверенным восстановлением (2.8), `SECURITY.md`, `CODEOWNERS`, Dependabot (2.9).

## Этап 4. Версия 1.0

| # | Задача | Размер |
|---|---|---|
| 4.1 | **Несколько устройств.** Связанные устройства, как в Signal: у личности несколько device-ключей; знакомство и сообщения рассылаются каждому устройству; синхронизация истории и контактов между своими устройствами; привязка нового устройства по QR. Нужно изменение протокола (v3) и сервера (сессии на устройство вместо одной на личность). | XL |
| 4.2 | **Push-уведомления** — первая крупная задача после запуска. Web Push для PWA и уведомления Android (FCM или UnifiedPush) с минимумом данных: сервер знает только, что «есть новое», без отправителя и содержимого; токены push не связаны с `PeerId` открыто. | L |
| 4.3 | **Скрытие метаданных.** Sealed sender для онлайн-сообщений, чтобы gateway знал только получателя; знакомство без раскрытия личности спрашивающего; ротация onion-ключа signaling; секреты inbox по эпохам; рекомендации и конфигурация для отдельного оператора relay. | L |

## Решено не делать

- **Прямое P2P-соединение (NAT traversal).** Раскрывает IP собеседнику; удалено в фазе A.
- **WebDriver-тесты десктопа.** Нативный диалог и микрофон ими не управляются; путь после устройства покрыт тестами через IPC.
- **Nix flake.** Второй, непроверяемый способ сборки; удалён.
