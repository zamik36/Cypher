# Архитектура «Шифра»

Мессенджер с шифрованием end-to-end, без регистрации и телефона. Личность — это ключ Ed25519, который создаётся на устройстве и восстанавливается по фразе из 24 слов. Сервер пересылает непрозрачные байты и не может прочитать ни сообщения, ни файлы.

Протокол описан в [protocol-v2.md](protocol-v2.md), модель угроз — в [threat-model.md](threat-model.md), цифры производительности — в [performance.md](performance.md).

## Общая схема

```text
 Десктоп / Android (Tauri)            Браузер (PWA)
 cypher-client ─┐                     Web Worker: cypher-wasm ─┐
                │ TLS :9100                          WSS /ws   │
                ▼                                              ▼
            ┌────────────── gateway (N узлов) ──────────────┐
            │ сессии, пересылка Send → Recv, rate limit      │
            └──────┬───────────────────────────┬─────────────┘
                   │ NATS peer.<id>            │ NATS sig.req
                   ▼                           ▼
            другие узлы gateway          signaling ── Redis
                                            ▲       (ключи, ссылки, inbox)
                                            │ NATS sig.onion
 анонимные запросы клиента ──TLS/WSS──► relay
 (десктоп — через Tor)
```

- **gateway** принимает клиентов по TLS (нативные) и WebSocket (браузер). Он проверяет владение ключом (challenge-response) и пересылает кадры между пирами. Получатель может быть подключён к другому узлу — тогда кадр идёт через NATS-субъект `peer.<id>`. Запросы к signaling проходят как NATS request/reply на `sig.req`. Состояния, кроме открытых соединений, нет.
- **signaling** хранит в Redis только то, что нужно для встречи и офлайн-доставки: prekey-бандлы, ссылки-приглашения и слепые inbox'ы. Сам сервис без состояния; единственный секрет на диске — onion-ключ.
- **relay** — один onion-хоп для анонимных запросов к inbox. Он видит адрес клиента, но не содержимое запроса; signaling видит запрос, но не адрес. Relay без состояния.
- **NATS** — шина между сервисами. У каждого сервиса свой пользователь с минимальными правами (`deploy/nats.conf`); signaling, например, не может ничего опубликовать сам.

## Крейты

| Крейт | Роль |
|---|---|
| `cypher-types` | Идентификаторы (`PeerId`, `LinkId`, `MsgId`, `FileId`), ошибка, общие константы. Работает и в WebAssembly. |
| `cypher-wire` | Протокол v2 между клиентом и сервером: кадры `[kind][req_id][поля]`, разбор без копирования. Единственное, что понимает сервер. |
| `cypher-crypto` | Личности, X3DH, Double Ratchet, sealed sender, onion-запросы, шифрование файлов по чанкам, файл личности на Argon2id. |
| `cypher-core` | Ядро клиента без ввода-вывода (sans-IO): все решения протокола и криптографии. На вход — события, на выход — упорядоченный список эффектов. |
| `cypher-client` | Нативный драйвер ядра на tokio: SQLite, файлы, переподключения, Tor (arti). |
| `cypher-wasm` | Сборка ядра для браузера; типы эффектов генерирует в `.d.ts`. |
| `cypher-media` | Голосовые: захват микрофона (cpal), Opus (libopus), WebM-мультиплексор, волна. |
| `cypher-tls` | TLS-конфиги rustls для сервисов и клиентов, dev-сертификаты. |
| `cypher-transport` | Кадрирование поверх TLS (`[u32 длина][кадр]`) и общий сервер соединений. |
| `cypher-server-kit` | Общее для сервисов: конфиг, NATS, метрики Prometheus, rate limit, секреты, трейсинг, останов. |
| `services/*` | gateway, signaling, relay: каждый — библиотека с `run(config, shutdown)` и тонкий `main`. |
| `apps/desktop/src-tauri` | Tauri-оболочка: команды IPC, схема `cypher-media://` для воспроизведения, запись голоса. |
| `tools/*`, `tests/*` | Нагрузочный тест, храповик покрытия (`xtask`), сквозные сценарии (`tests/e2e`), k6 (`tests/load`). |

Фронтенд общий: `packages/ui` (SolidJS) работает через интерфейс `Platform`. Его реализуют `apps/desktop/src/tauri.ts` (IPC Tauri) и `apps/pwa/src/web/platform.ts` (RPC с Web Worker).

## Ядро как машина эффектов

`cypher-core` не открывает сокетов, не читает файлов и не смотрит на часы. Драйвер передаёт в `Core::handle(input, now)` одно из событий:

- соединение открыто или закрыто, пришёл кадр;
- команда пользователя (отправить текст, файл, принять файл, отметить прочитанным…);
- прочитан чанк файла, тик таймера.

В ответ ядро возвращает эффекты, и драйвер обязан выполнить их **строго по порядку**:

| Эффект | Что делает драйвер |
|---|---|
| `Persist` | Атомарно записывает пакет строк в хранилище. |
| `Transmit` / `Anonymous` | Отправляет кадр в gateway или в relay. |
| `Emit` | Передаёт событие в UI. |
| `ReadChunk`, `OpenSink`, `WriteChunk`, `CloseSink` | Файловый ввод-вывод передачи. |
| `Disconnect` | Закрывает соединение, при необходимости с переподключением. |

Главный инвариант: запись на диск становится durable раньше, чем следующий за ней кадр уходит в сеть. Поэтому состояние ratchet не может «убежать» от сохранённого после сбоя. Оба драйвера — нативный (`cypher-client`) и браузерный (`apps/pwa/src/web/effects.ts`) — выполняют один и тот же контракт. Порядок проверен тестами с обеих сторон.

Раз ядро одно, протокол, криптография, очереди, повторы и передача файлов одинаковы на всех платформах. Сценарии ядра (`cypher-core/tests/scenarios.rs`) гоняют двух клиентов в памяти без сети.

## Потоки данных

**Знакомство.** Хозяин создаёт ссылку (`CreateLink`, живёт 24 ч) и показывает её или QR в виде `<код>-<отпечаток ключа хозяина>`. Гость отправляет серверу только код и получает в ответ `PeerId`. Если отпечаток не совпадает с этим `PeerId`, знакомство отклоняется (`ShareLink`). Затем гость забирает prekey-бандл хозяина, подписанный этой же личностью. Затем выполняет X3DH и сразу шлёт первое сообщение с заголовком инициализации — без лишнего раунда. С этого момента у пары есть Double Ratchet.

**Сообщение онлайн.** Клиент шифрует конверт ratchet'ом и отправляет `Send{to, body}`. Gateway ставит отправителя из аутентифицированной сессии (подделать `from` нельзя) и доставляет `Recv` получателю: локально или через узел, на котором получатель подключён. Если нужно, отвечает `SendAck`: доставлено, получатель офлайн или перегружен.

**Сообщение офлайн.** При `Offline` клиент запечатывает конверт для inbox получателя (sealed sender: сервер не видит отправителя). Затем кладёт его через relay (onion) в Redis. Получатель при подключении забирает inbox тоже через relay: сначала захватывает пакет, потом подтверждает. Адрес inbox — хэш секрета, который знает только владелец; писать туда могут все, кому он сообщил адрес, а читать — только владелец.

**Файл.** У каждого файла свой случайный ключ AES-256-GCM. Ключ едет внутри зашифрованного дескриптора, поэтому чанки не трогают ratchet и шифруются независимо. Отправитель режет файл на чанки по 256 КиБ (медиа — по 64 КиБ) и держит окно в 8 МиБ. Получатель подтверждает чанки выборочно (SACK). Передача возобновляется после перезапуска с того места, где остановилась.

**Голосовые и кружочки.** Это файлы с метаданными: длительность, волна или постер. Короткие (до 32 КиБ) едут прямо в конверте. На устройстве медиа хранится зашифрованным и расшифровывается по кускам при воспроизведении. На десктопе это делает схема `cypher-media://` с Range-запросами, в браузере — Worker, который отдаёт blob URL.

## Хранение на устройстве

- **Личность** — файл, зашифрованный AES-256-GCM под ключом Argon2id от пароля. Параметры KDF входят в associated data, поэтому их нельзя незаметно ослабить.
- **Состояние** — семь таблиц: `meta`, `peers`, `outbox`, `transfers`, `messages`, `message_status`, `media`. Каждая строка запечатана Vault — AEAD с ключом, выведенным из сида личности.
  - Нативно таблицы лежат в SQLite.
  - В браузере — в IndexedDB со строгой durability.
- **Файлы.** Нативно — позиционная запись в целевой файл. В браузере входящие файлы пишутся в OPFS, а исходящие хранятся в IndexedDB, чтобы передачу можно было возобновить после перезагрузки вкладки.
- **Сид в браузере** не покидает память WebAssembly. JS видит только зашифрованные строки и готовые кадры.
- **Версии.** Каждая запись начинается с версии своей схемы (`Record::VERSION`); старые версии читаются через `Record::upgrade`. Нечитаемая запись пропускается с предупреждением и не мешает запуску. Данные от более новой версии приложения останавливают запуск: работа поверх них могла бы испортить состояние. База SQLite дополнительно помечена `user_version`.

## Масштабирование и эксплуатация

- **Gateway рассчитан на горизонтальное масштабирование.** Узлы не знают друг о друге и обмениваются кадрами через NATS; в CI нагрузка идёт на два узла. Стандартный деплой ([deploy.md](deploy.md)) поднимает по одному экземпляру каждого сервиса; несколько gateway за балансировщиком — в разделе «Позже» [roadmap](roadmap.md).
- **Одна личность — одна сессия.** Новый вход вытесняет старый, в том числе на другом узле (сообщение `Superseded`). Несколько устройств на одной личности — этап 4 roadmap.
- **Лимиты gateway.** До 100 000 соединений на узел, 2000 кадров/с и 64 МиБ/с на соединение. Бездействие — 60 с, аутентификация — 10 с.
- **Метрики.** Каждый сервис отдаёт метрики Prometheus: соединения, отказы, задержки, метрики рантайма tokio. Готовые дашборды Grafana и сбор логов (Loki, Alloy) лежат в `deploy/`.
- **Производительность.** Измеренный узел держит 10 000 клиентов с p99 пересылки 2,5 мс при 24,5 КБ на соединение. Подробности — в [performance.md](performance.md).
